Concepts

Race condition

A race condition happens when the result of an operation depends on the relative timing of concurrent executions. The classic shape is read → decide → write: two transactions read the same value, both decide based on what they read, and both write — the second write is computed from stale data. Races are timing-dependent, which is why RaceLab uses coordinated starts, artificial delays and step-by-step checkpoints to make them reproducible.

Lost update

Two withdrawals of 800.00 read a balance of 1000.00, each computes 200.00 and writes it. Both are confirmed, yet the balance only decreased once: one update was lost. Under PostgreSQL READ COMMITTED a plain SELECT followed by UPDATE … SET balance = :computed allows this. Fixes: an atomic conditional update, optimistic locking (version column), pessimistic locking (SELECT … FOR UPDATE) or SERIALIZABLE with retries.

Deadlock

Transaction A locks row 1 and waits for row 2 while transaction B locks row 2 and waits for row 1. Neither can proceed. PostgreSQL runs its deadlock detector after deadlock_timeout (1 s by default), aborts one victim with SQLSTATE 40P01 and lets the other continue. The Lock graph tab draws the wait-for cycle and marks the victim. Prevention: acquire locks in a consistent global order (lock ordering), keep transactions short, and retry victims.

Write skew

Two transactions read an overlapping set of rows, check an invariant (for example, "at least one doctor on call"), and each updates a different row. Neither write conflicts with the other, so snapshot isolation lets both commit and the invariant breaks. PostgreSQL REPEATABLE READ allows write skew; SERIALIZABLE detects the dangerous dependency and aborts one transaction with SQLSTATE 40001.

Isolation levels

The SQL standard defines levels by the anomalies they forbid. PostgreSQL is stricter in practice:

Level Dirty read Non-repeatable read Phantom read Write skew
Read UncommittedNot possible (behaves as Read Committed)PossiblePossiblePossible
Read CommittedNot possiblePossiblePossiblePossible
Repeatable ReadNot possibleNot possibleNot possible (snapshot)Possible
SerializableNot possibleNot possibleNot possibleNot possible (SSI aborts with 40001)
  • Read Uncommitted is accepted but treated as Read Committed: PostgreSQL never exposes uncommitted data.
  • Read Committed (default) takes a new snapshot per statement.
  • Repeatable Read is snapshot isolation: one snapshot per transaction, so phantoms are not visible; concurrent updates to the same row fail with 40001.
  • Serializable uses Serializable Snapshot Isolation (SSI): it tracks read/write dependencies and aborts one transaction with 40001. Clients must retry.

Optimistic vs pessimistic locking

Optimistic locking reads without locks and validates at write time with a version column (UPDATE … WHERE id = ? AND version = ?). Zero rows updated means a conflict: the transaction is rejected or retried. It shines with low contention and fails fast under high contention. Pessimistic locking takes the row lock up front (SELECT … FOR UPDATE), so competitors queue. It guarantees progress for the lock holder but adds lock waits, can deadlock when lock order differs, and holds locks during any slow work inside the transaction.

Atomic conditional update

Move the decision into a single statement: UPDATE account SET balance = balance - :amount WHERE id = :id AND balance >= :amount. The database evaluates the condition and the write under the same row lock, so there is no stale read. Check the affected row count to know whether the business rule rejected the operation. The "unguarded" variant (without the WHERE balance >= …) avoids lost updates but can still break the "balance ≥ 0" invariant.

Advisory locks

PostgreSQL advisory locks (pg_advisory_xact_lock(key)) are application-defined mutexes managed by the database. They coordinate work that does not map to a single row (for example, "only one job per customer") across every application instance sharing the database. Transaction-scoped variants release automatically at commit/rollback.

Redis locks and fencing tokens

A Redis lock (SET key value NX PX ttl) coordinates instances that do not share a transaction. Its weakness is the TTL: a client paused longer than the TTL (GC, network) still believes it holds the lock while another client acquires it. A fencing token — a monotonically increasing number issued with each lock — lets the storage reject writes carrying an older token, so a stale lock holder cannot corrupt data.

Idempotency keys

Retries and double clicks deliver the same request twice. Storing a client-supplied idempotency key with a UNIQUE constraint (in the same transaction as the effect) makes the second attempt fail with 23505 or return the stored result, so the effect happens exactly once.

Transactional outbox

Writing to the database and publishing a message are two systems: a crash between them loses or duplicates the message. The outbox pattern writes the message to an outbox table in the same transaction as the business change; a relay publishes it afterwards and marks it as sent. Delivery becomes at-least-once, so consumers must be idempotent — the "naive consumer" strategy shows what happens when they are not.

Reading the timeline

  • Each column is a worker (one transaction at a time); the first column holds experiment-level events.
  • Rows are ordered by elapsed time since the experiment started; the gutter shows the elapsed milliseconds and the gap since the previous event. Zoom changes how many pixels a millisecond takes.
  • Every card has an icon and a text label: read write wait / lock request / checkpoint conflict / deadlock / inconsistency commit rollback.
  • Cards marked observed in DB come from PostgreSQL itself (pg_blocking_pids, pg_stat_activity, SQLSTATE). The others are instrumented by the application code.
  • The yellow bar to the left of a column means the worker holds a lock; the dashed bar means it is waiting for one.
  • The state table compares initial, current and expected values. INVÁLIDA means a business invariant was violated.

Step-by-step mode

Workers pause at named checkpoints (before read, after read, before write, before commit…). "Next step" releases the suggested worker; "Release" releases a specific one; "Resume" leaves step mode. A worker blocked on a database lock cannot reach its next checkpoint until the lock is released — that is the database speaking, not the UI. Checkpoints are released automatically when the step timeout expires.

Architecture

  • The browser only calls same-origin /api/**; Nginx proxies to the BFF with buffering disabled for the event stream.
  • The BFF forwards requests unchanged, adds X-Correlation-Id and routes to an instance via X-RaceLab-Instance.
  • Each experiment runs on isolated, namespaced data, so concurrent experiments do not interfere with each other.

Limitations

  • Point-in-time inspector. The Transaction Inspector polls pg_stat_activity and pg_locks; states shorter than the polling interval are not captured.
  • Artificial delays. Delays widen race windows so anomalies are reproducible; real systems hit them less often, but they still happen.
  • Local hardware. Timings depend on the machine, Docker resources and PostgreSQL configuration.
  • No universal benchmark. Comparator results describe this scenario under this load; they do not declare a universally best strategy.
  • Step mode timeouts. Paused checkpoints are released automatically after the step timeout to avoid holding database locks forever.
  • Concurrency cap. At most 3 experiments run concurrently per backend instance (HTTP 409 TOO_MANY_EXPERIMENTS); limits on threads, transactions and delays are enforced by the backend.
  • Reconstructed graphs. When PostgreSQL does not report a lock graph, it is reconstructed from application events and labelled as such.
